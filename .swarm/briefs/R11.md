# R11 — atomicWrite stages at a fixed name (Tier 3)

## The defect

`internal/services/storage/storage.go:442`:

```go
tmpPath := path + ".tmp"
if err := os.WriteFile(tmpPath, data, perm); err != nil { return err }
return os.Rename(tmpPath, path)
```

The staging name derives solely from the destination. `Storage.WriteFile` holds
only `dataMu.RLock()` — a SHARED lock — so concurrent writers to one path are
permitted by design and all race on the same staging file.

Two observed consequences, both reproduced by the oracle against current code:

1. **Spurious failure.** Writer A renames the staging file away; writer B's
   rename then fails with `no such file or directory`. `WriteFile` returns an
   error for a write that was perfectly valid.
2. **Torn content.** Each `os.WriteFile` truncates and rewrites the same
   staging file; with payloads larger than one syscall the survivor can hold a
   mixture of two writers' bytes, with every call reporting success.

## Why it is currently unreachable in production

Every caller happens to serialize externally — dataloader via its `writeMu`,
accounts via `Mutate` (added by R1), the settings manager via its own lock. The
invariant is undocumented and unenforced: `atomicWrite`'s correctness silently
depends on every present and future caller doing its own serialization. One
unserialized caller reintroduces silent corruption in a money-data store.

## The precedent, 50 lines away in the same file

`CreateExclusive` (`storage.go:392`) already stages correctly:

```go
f, err := os.CreateTemp(dir, filepath.Base(path)+".tmp-*")
```

Adopt that approach. Do not invent a different one.

## Scope

- Fix `atomicWrite` so concurrent writers to one path cannot share a staging
  file, and a completed write leaves no staging file behind.
- Preserve the single-writer contract exactly: same content, same permissions,
  a rewrite replaces rather than appends, and the write remains atomic from a
  reader's point of view (readers never observe a partial file).
- Clean up the staging file if the write fails, so a failed write does not
  litter the data directory.

**Out of scope — report, do not fix.** `migration.go:247`, `migration.go:275`
and `auth.go:92` use the same fixed-`.tmp` pattern. They have different
concurrency exposure and separate blast radius. Name them in your report; do
not change them.

Do NOT change `Storage.WriteFile`'s locking, `BeginShared`, `BeginExclusive`,
or the lock ordering documented at `storage.go:520-560`. This is a staging-name
fix, not a concurrency-model change.

### The atomicWrite fix itself is CORRECT. Do not redo it.

Both lanes confirmed it independently and thoroughly: 129 spurious rename errors
pre-merge vs 0 after; 1079 partial reader observations pre-merge vs 0; failure
cleanup proven at staging-create, write, chmod and rename; permissions, encryption
round-trip, Rename-not-Link and the locking model all verified unchanged.

### What broke

`internal/services/backup/snapshot.go:269`:

```go
// Skip atomicWrite leftovers and encryption-state files.
if strings.HasSuffix(base, tmpSuffix) {   // tmpSuffix = ".tmp"
```

The comment names `atomicWrite` explicitly. The OLD staging name `path+".tmp"`
matched that suffix. The NEW name `<base>.tmp-<random>` does not:

    sidecar.json.tmp             endswith(".tmp") = True
    sidecar.json.tmp-2496562633  endswith(".tmp") = False

Four consumers depend on it — `handlers/backup/handlers.go:268` and `:377`,
`services/restore/restore.go:119`, `services/backup/snapshot.go:225`. A
crash-orphaned staging file is now swept into backup zips and loses restore-time
prune protection, so garbage round-trips permanently into backups of a
money-data store.

`TestSkipPredicate_FilesUnderSkipListedDirs` gives false confidence: it hardcodes
the literal `"foo.tmp"` instead of deriving from what `atomicWrite` emits, so it
kept passing while the real contract broke.

### Required fix — make the contract compile-time, not string-matched

The root problem is that two packages agreed on a filename convention through a
string literal, which neither the compiler nor a package-scoped oracle can see.

1. Export a predicate from `internal/services/storage` — e.g.
   `func IsStagingName(base string) bool` — that recognises the staging names
   `atomicWrite` and `createExclusive` actually produce. Define it next to the
   code that produces them so the two cannot drift.
2. Have `backup.SkipPredicate` call it instead of matching a literal suffix.
   Keep skipping the old `.tmp` form too: staging files orphaned by a crash
   BEFORE this change still exist in real data directories.
3. Fix `TestSkipPredicate_*` to derive its fixture from a name the real staging
   path produces, not a hand-written literal.

Do not simply add `".tmp-"` as a second literal in snapshot.go. That repeats the
same mistake and the next change to the staging name breaks it again.

### Evidence required, persisted in the tree

- A test in the backup package proving `SkipPredicate` skips a name produced by
  the real staging path, derived not hardcoded.
- A test proving the OLD `.tmp` form is still skipped (pre-existing orphans).
- A test proving a legitimate data file whose name merely contains `.tmp` is NOT
  skipped, if that distinction matters — say which way you resolved it.
- Mutation check per fix, on a scratch copy outside the repo.
