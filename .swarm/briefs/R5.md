# R5 — get_balance_projection must honour as_of (Tier 2)

**Depends on R3, which lands first in the same function. Rebase onto it.**

## The defect

`internal/services/mcpsvc/ledger/accounts.go` parses an explicit `as_of` for
`get_balance_projection` (around line 211) and passes it to `accounts.Project`
— but the recurring-payment input is built by `recurringForProjection`, which
calls `insights.DetectRecurring(ts)`.

`DetectRecurring` is defined as `DetectRecurringAt(ts, time.Time{})`
(`internal/services/insights/recurring.go:196`), and a zero reference date
falls back to the set's own `MaxDate`. Read the `DetectRecurringAt` doc comment
— it states that `referenceDate` does two distinct jobs: it truncates the
history detection sees, **and** it is the freshness "now" each candidate series
is checked against.

Consequences:

- A **historical** `as_of` runs detection over the whole ledger including
  transactions after that date, so the forecast uses future evidence — and can
  schedule nothing inside its own window.
- A **future** `as_of` evaluates recurrence freshness against the ledger
  maximum rather than the requested date.

## Scope

In `get_balance_projection` only:

- Truncate the active transaction set at `as_of` before projecting.
- Call `insights.DetectRecurringAt(ts, asOf)` instead of `DetectRecurring(ts)`.

`recurringForProjection` needs the as-of date threaded in. `get_accounts` uses
`time.Now()` and is not in scope beyond R3's active-set change.

## Acceptance

- A historical `as_of` schedules recurrence from evidence at or before that date
  only, and **can** schedule inside its window (assert a non-empty schedule on a
  fixture where the old code produced none).
- A future `as_of` evaluates freshness against the requested date, not the
  ledger maximum.
- With no `as_of` supplied, output is unchanged from current behaviour on a
  fixture — pin this so the default path cannot drift.
- `go build ./... && go vet ./... && go test -race ./...` clean.
