# U8 attempt 1 — one date range propagated across pages

## What changed

- `internal/templates/render.go`
  - Added `reflect` import.
  - Registered `withRange` in `getFuncMap()`.
  - Added `withRange(href string, pageData interface{}) string`,
    `extractDateRange(pageData interface{}) (string, string)`, and
    `stringOrEmpty(v interface{}) string`.
  - `withRange` appends `?start=<start>&end=<end>` (URL-query-encoded via
    `url.Values`) to `href` only when BOTH `StartDate` and `EndDate` are
    non-empty strings on the page-data value it's given; otherwise it
    returns `href` unchanged.
  - `extractDateRange` reads `StartDate`/`EndDate` off whatever shape the
    calling handler's page data actually is: `map[string]interface{}`
    (dashboard/explorer/insights/majorexpenses/whatif/duplicates/
    filemanager all use this) via direct map lookup, or a struct
    (accounts, transfers use a private `pageData` struct with no such
    fields) via `reflect.FieldByName`, walking through pointers. A missing
    map key or absent/non-string struct field resolves to `""`, never a
    template-execution error — this was the key design constraint: passing
    the WHOLE `.` (the actual page-data value) into `withRange` as a Go
    function argument is always a valid value, unlike a direct
    `{{.StartDate}}` field access in the template, which would hard-error
    template execution on accounts/transfers (struct has no such field)
    with `html/template`'s default `missingKey` behavior for maps only
    softening *printed* output, not function-argument evaluation.

- `web/templates/layouts/base.html`
  - Changed ONLY the `href` attribute of the four Money-group nav links
    (Dashboard, Explorer, Insights, Major Expenses) in BOTH the desktop bar
    (lines ~79-90 pre-edit) and the mobile menu (lines ~156-159 pre-edit)
    from a bare path to `{{withRange "<path>" .}}`.
  - Plan (`/whatif`) and Setup (`/accounts`, `/transfers`, `/filemanager`,
    `/duplicates`) links are UNCHANGED (still bare hrefs).
  - No other markup touched: U9's group structure, labels, `aria-current`,
    `role="group"`/`aria-labelledby`, mobile toggle, and the duplicate-count
    badge are all preserved byte-for-byte apart from the 8 `href` edits.

- `internal/templates/render_nav_range_test.go` (new)
  - There was no existing base-layout/nav render test file, so this is it
    (per the task instruction to put tests "where the existing
    base-layout/nav render tests live").
  - `TestBaseNav_PropagatesRangeOnMoneyGroupLinks`: renders "base" with

    all 8 Money-group anchors (4 links x desktop+mobile) carry both

## Why `.StartDate`/`.EndDate` field access in the template was rejected

All four range handlers already set `pageData["StartDate"]` /
`pageData["EndDate"]` as `"YYYY-MM-DD"` strings (dashboard/explorer/
insights: `time.Time.Format("2006-01-02")`; majorexpenses:
`formatDateInputValue`, same format, `""` on a zero time). So `.StartDate`
already existed everywhere it needed to for the four range pages, and I
could have written `{{withRange "/dashboard" .StartDate .EndDate}}`. I
rejected that shape because `base.html`'s nav renders on EVERY page via one
shared "base" template body, and two pages (`internal/handlers/accounts`,
`internal/handlers/transfers`) pass a private `pageData` STRUCT with no
`StartDate`/`EndDate` field at all (confirmed by reading both files). Direct
field access on a struct that lacks the field is a template EXECUTION ERROR
(`can't evaluate field StartDate in type accounts.pageData`), which I
reproduced with a throwaway test before settling on the final design (see
the "both-ends" note below) — that would have broken `/accounts` and
`/transfers` entirely. Passing the whole page-data value (`.`) into the Go
function instead sidesteps the template engine's field-lookup rules
altogether; my Go code decides map-vs-struct and missing-vs-present using
ordinary Go, which never errors on absence.

## Both-ends check performed while developing

Before landing the final `withRange(href string, pageData interface{})`
signature, I ran the test suite with an EARLIER draft that called
`{{.StartDate}}` directly in the template as a function argument, and with
`{{index . "StartDate"}}` (which also fails on the accounts/transfers
STRUCT case since `index` requires map/slice/array). Both drafts failed
`TestBaseNav_StructPageDataRendersBareLinks` (or its precursor) with a
template-execution error, confirming the test correctly detects the two
naive implementations the task worried about. The final `.`-passing
implementation passes it.
