# R3 — Resolved duplicates must not be counted in balances (Tier 2)

## The defect

`models.TransactionSet.Active()` (`internal/models/transaction.go:466`) filters
out `Suppressed` rows, and its own doc comment says aggregation and reporting
call sites should use it to avoid double-counting near-duplicate pairs the user
has resolved. `accounts.BalanceAt` (`internal/services/accounts/balance.go:46`)
sums every matching row and performs no `Suppressed` check — filtering is the
caller's job.

Two callers pass the raw set instead:

- `internal/handlers/dashboard/handlers.go:114` — passes `data.Transactions`,
  even though line 101 of the same function correctly uses `data.Active()` for
  the period comparison.
- `internal/services/mcpsvc/ledger/accounts.go` — `get_accounts` (around line
  87) and `get_balance_projection` both take `ts.Transactions` raw.

So a payment the user has already resolved as a duplicate is counted twice in
account balances, low-balance warnings, and funding projections.

## Scope

Pass the active set at those call sites.

**Amended for attempt 2 (2026-08-19).** Attempt 1 fixed the balance argument at
dashboard/handlers.go:114 but left the recurring argument on the same line
unfiltered, and both verification lanes independently reproduced a real defect
from it. The line reads:

    buildAccountsCard(store, data.Active().Transactions, asOf, detectRecurringForDashboard(data, asOf))

`detectRecurringForDashboard` (internal/handlers/dashboard/accounts_card.go:241)
passes straight to insights.DetectRecurringAt with no filtering, while the MCP
twin `recurringForProjection` DOES call .Active(). Two paths that must agree
disagree, and the projection consumes the unfiltered one.

Measured consequences, both reproduced on real fixtures:
  - A suppressed row's near-zero interval can reclassify a series monthly ->
    ongoing; Project's frequencyIntervalDays returns ok=false for ongoing, so
    the outflow is dropped and the dashboard reports "healthy, no top-up"
    where the truth was a crossing needing $400.
  - A suppressed row can also be the third leg that promotes a two-payment
    history into a "monthly" series AND inflate its amount (916.67 observed),
    producing a crossing and a $200 top-up that exist only because of a row
    the user already resolved.

Fix it at one of the two places, and make the dashboard and MCP paths agree. Do **not** change `BalanceAt`,
`Freshness`, `Project` or `Active()` — the filtering belongs to the caller by
design, and changing the service would break the explorer.

**The explorer must keep the raw slice.** It deliberately shows suppressed rows
so the user can see and undo a suppression. Do not touch it.
