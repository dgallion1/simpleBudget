## What changed
1. One product name = **simpleBudget**: `<title>{{.Title}} - simpleBudget</title>`,
   header wordmark link text, footer `simpleBudget &copy; {{now.Year}}`.
   `grep -niE 'Financial Dashboard|Budget Dashboard' web/templates/layouts/base.html`
   → 0 matches (verified below). NOTE: `web/templates/pages/unlock.html`
   (title + heading "Financial Dashboard") and `cmd/server/main.go:340`
   (`log.Printf("Starting Budget Dashboard on %s", ...)`) still say the old
   names — out of scope per the task's explicit "ONE FILE" restriction;
   flagging for backlog/U15 sweep or a follow-up task, not fixed here.

2. Three labelled nav groups, desktop and mobile, links redistributed exactly
   as specified:
   - **Money**: Dashboard, Explorer, Insights, Major Expenses
   - **Plan**: What-If
   - **Setup**: Accounts, Transfers, File Manager, Duplicates (badge kept,
     still gated by `{{if .UnresolvedDuplicateCount}}`, unchanged condition)

   Desktop: each group is a `<div role="group" aria-labelledby="nav-group-*">`
   with a visible eyebrow `<span id="nav-group-*" class="text-label uppercase
   text-white/60">` (U6 `label` token, no `text-[11px]`/hue literal — uses the
   existing `white/60` opacity utility already used elsewhere in this nav).
   A `aria-hidden="true"` vertical rule (`h-6 w-px bg-white/20`) separates
   groups visually; it carries no text, so nothing is hidden from anyone —
   it's a decorative divider, same pattern already in use for icon-only
   elements elsewhere in the app.

   Mobile: each group is `<div role="group" aria-labelledby="mobile-nav-group-*">`
   with a visible `<p id="mobile-nav-group-*" class="px-3 text-label uppercase
   text-white/60">` label above its stacked links, `space-y-4` between groups.

   Design choice: labels are `role="group"` + `aria-labelledby` pointing at a
   VISIBLE, non-hidden text node (not `aria-label` on an invisible span, and
   not a semantic `<h2>`/`<h3>` heading — introducing real headings inside the
   nav would sit before every page's own `<h1>` in document order and risks a
   heading-hierarchy complaint under ACCESSIBILITY.md point 1; the spec's own
   wording in §2i's accessibility bullet explicitly offers `role="group"` +
   `aria-label` as one of two acceptable patterns). This satisfies "labelled"
   and "associated with their group" mechanically without adding heading noise.

3. `aria-current="page"` added to every nav link (desktop AND mobile) sharing
   the existing `{{if eq .ActiveTab "..."}}` condition that already drives the
   `bg-white/20` active-state class — same source of truth, no new state.
   The Duplicates link (desktop+mobile) only renders at all when
   `.UnresolvedDuplicateCount` is truthy (pre-existing, unchanged gate); with
   0 unresolved duplicates in the verify data, visiting `/duplicates` shows no
   nav-current link for it — this is pre-existing behavior, not introduced
   here, and was confirmed by probe (see verification below).

4. `#mobile-nav-toggle` — `id`, `aria-label`, `aria-expanded`, `aria-controls`
   left byte-identical; `#mobile-nav` `id` unchanged; `web/static/js/base.js`
   (untouched) toggles `.hidden` and flips `aria-expanded` purely by ID, so
   restructuring `#mobile-nav`'s children (grouped now) does not affect it.
   Verified via a real `Enter`-key press on the focused toggle button at
   390px: `aria-expanded` flips false→true and the panel's `hidden` class is
   removed.
