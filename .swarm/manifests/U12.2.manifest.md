# U12 manifest — Accounts as summary cards (attempt 2)

Fixes checker-a11y's attempt-1 FAIL (conceded; ruling U-2026-09-05n in
`.swarm/U-RUN-SPEC.md` §10): with the Edit/Add forms hidden behind U12's
disclosures, an EDIT-form validation error stayed stranded on the
unrelated, still-collapsed Add form because the accounts error model had
no account scoping.

## Root cause (confirmed by reading the code, matches the ruling)

- `handleUpdate`'s error path (`internal/handlers/accounts/handlers.go`)
  set `data.Error` but never `data.ErrorField` (it discarded `formData`
  with `_`) and had no account id on `pageData` at all.
- The Add form's `data-focus-target="id"`/`"name"` attributes were
  UNCONDITIONAL, so `accounts.js`'s `target.querySelector('[data-focus-
  target]')` always matched the Add form's field first — even for an
  edit-form error, even though `handleUpdate` didn't populate `ErrorField`
  anyway.
- The per-account edit-form "name" field's own gate,
  `{{if and (eq $root.ErrorField "name") (eq $root.ConfirmDeleteID "")}}`,
  had no per-account scoping either: if `ErrorField=="name"` were ever
  true, EVERY account's edit-name field in the `{{range}}` would have
  matched simultaneously.

This is a "handlers untouched" exception the ruling explicitly grants: a
DISPLAY-ONLY error-scope addition, not a CRUD/save change. No account
mutation logic (create/update/delete/anchor add/anchor delete) was
touched.

## What changed

`internal/handlers/accounts/handlers.go`:
1. Added `ErrorAccountID string` to `pageData` (next to `ErrorField`):
   `""` scopes an error to the Add form; a non-empty account ID scopes it
   to that account's Edit form (or its anchor form).
2. `handleUpdate`'s error path now captures `formData` from `applyForm`
   (was `_`) and sets `data.ErrorField = fd.errorField` (previously never
   set at all — a second, independent bug this fix also closes: an edit
   validation error used to render NO `ErrorField`, so no field was ever
   flagged `aria-invalid` for an edit-form error, not just the wrong one)
   plus `data.ErrorAccountID = id`.
3. All four `handleAddAnchor` error paths (missing date/amount, bad date
   format, bad amount format, and the final `accounts.Mutate` failure) now
   also set `data.ErrorAccountID = id`.
4. `handleCreate` is unchanged — it already set `ErrorField`; leaving
   `ErrorAccountID` at its zero value `""` is exactly the "Add form
   errored" scope.

`web/templates/pages/accounts.html`:
1. Add-form "id", "name" and "low_balance_threshold" fields: `data-focus-
   target`/`aria-invalid` now additionally require `(eq .ErrorAccountID
   "")`, so an edit-form or anchor-form error (which sets a non-empty
   `ErrorAccountID`) can no longer match the Add form's fields. (The
   `low_balance_threshold` field name is shared with the edit form via the
   same `parseAccountForm` path, so it needed the same guard even though
   the ruling's fix list named only id/name explicitly — same defect
   class, same fix shape.)
2. Add-form disclosure: the button's `aria-expanded` and the panel's
   `hidden` attribute both now derive from `(and .ErrorField (eq
   .ErrorAccountID ""))` — a failed add-account submit opens the panel
   server-side; a successful submit or an edit/anchor error leaves it
   collapsed.
3. Per-account Edit-form "name" field: the old, unscoped `(eq
   $root.ConfirmDeleteID "")` guard is replaced with `(eq
   $root.ErrorAccountID $acct.Account.ID)` — now only the ACCOUNT THAT
   ERRORED gets the focus target and `aria-invalid`.
4. Per-account Edit disclosure: introduced `$editErrored := and (eq
   $root.ErrorAccountID $acct.Account.ID) (or (eq $root.ErrorField "name")
   (eq $root.ErrorField "low_balance_threshold"))`, used for both the
   toggle button's `aria-expanded` and the panel's `hidden` attribute.
   The `ErrorField` restriction to "name"/"low_balance_threshold" (the two
   fields that actually live in this panel) is deliberate and goes beyond
   the ruling's literal wording (which keyed the reveal on
   `ErrorAccountID` alone): `handleAddAnchor` ALSO sets `ErrorAccountID`
   to the same account for an "anchor_date"/"anchor_amount" error, and the
   anchor form is NOT inside this panel (it stays visible, un-hidden, as
   before U12) — without the `ErrorField` restriction, an anchor-form
   error would have popped the unrelated, empty-of-errors Edit-settings
   panel open too. Verified by a new test (see below) that an anchor error
   leaves the Edit panel collapsed while still flagging the anchor field
   itself.

`web/static/js/accounts.js`: unchanged from attempt 1. `revealAncestorPanel`
is exercised as a no-op now that the server already renders the erroring
panel open — verified in the browser probe below (the field is focused
without JS needing to un-hide anything, because there is nothing left to
un-hide).

`internal/handlers/accounts/handlers_test.go`: added tests (all new; every
pre-existing test is byte-for-byte unmodified and green):
- `TestHandleUpdate_EmptyNameSurfaced_SetsErrorAccountID` — JSON-mode:
  edit error sets `ErrorField=="name"` and `ErrorAccountID==<the account>`.
- `TestHandleCreate_EmptyNameSurfaced_ErrorAccountIDEmpty` — JSON-mode:
  create error leaves `ErrorAccountID==""`.
- `TestHandleAddAnchor_InvalidDate_SetsErrorAccountID` — JSON-mode: anchor
  error sets `ErrorField=="anchor_date"` and `ErrorAccountID==<account>`.
- `TestHandleUpdate_RendererMode_ErrorRevealsOnlyErroringAccountsPanel` —
  renderer-mode, TWO accounts: an edit error on account A renders A's
  panel WITHOUT `hidden`, `aria-expanded="true"`, A's name field
  `data-focus-target`+`aria-invalid`; account B's panel stays
  `hidden`/`aria-expanded="false"`; the Add panel stays hidden.
- `TestHandleCreate_RendererMode_ErrorRevealsOnlyAddPanel` — mirror case:
  a create error opens the Add panel and leaves every account's Edit panel
  hidden.
- `TestHandleAddAnchor_InvalidDate_RendererMode_DoesNotOpenEditPanel` —
  proves the `$editErrored` field restriction: an anchor-form error leaves
  the Edit-settings panel hidden while still flagging `anchor_date`.
- `TestHandlePage_RendererMode_SummaryCard_ZeroAnchorAccount` — the
  coordinator's "runtime-exercise the zero-anchor branch" ask: seeds one
  account with no anchors and one with an anchor, asserts "No anchor set"
  and the formatted anchor amount both render.

collapsed. Scenario 2 (Add form, invalid submit): Add panel opens, `#acct-

re-rendered institution text) and NO panel is forced open — the disclosure
default (collapsed) holds when there is nothing to surface.
