# R6 — A second anchor on the same date must not silently lose (Tier 2)

**Depends on R1, which introduces the serialized `accounts.Mutate` API this
handler will be using. Rebase onto it and do your edit inside the Mutate
callback.**

## The defect

The accounts UI add-anchor handler (`internal/handlers/accounts/handlers.go`,
around line 254) appends unconditionally:

```go
accts[i].Anchors = append(accts[i].Anchors, models.BalanceAnchor{...})
sort.Slice(accts[i].Anchors, func(j, k int) bool { ... })
```

`latestAnchorAtOrBefore` (`internal/services/accounts/balance.go:166`) selects
with `if !found || ad.After(dayOf(best.Date))` — a **strictly later** day. On a
tie it therefore keeps the **first** anchor it encounters in slice order.

Two things follow, and the second is worse than a stale read:

1. Adding a second anchor for a date that already has one leaves the *old*
   amount driving every balance and projection, with no error shown.
2. `sort.Slice` is **not a stable sort**, so with two anchors on one day which
   one is encountered first is arbitrary and can differ between saves. Which
   balance is authoritative is nondeterministic, not merely stale.

The MCP path already does this correctly — `applyAnchor` in
`internal/services/mcpsvc/ledger/anchor.go` filters out same-day anchors before
appending, because the end-of-day balance is a single fact. The UI diverges
from it.

**Also part of this defect:** `latestAnchorAtOrBefore`'s doc comment claims
"Ties on the same day resolve to the last seen". The code does the opposite.
Correct the comment to match whatever the code does after your fix.

## Scope

Pick one and implement it fully:

- **Replace** — match the MCP path: filter same-day anchors, then append and
  re-sort. Preferred, because the two paths then agree.
- **Reject** — refuse the duplicate date with a field-level error.

If you choose rejection, the error must satisfy `ACCESSIBILITY.md`: associated
with the field programmatically, announced, and not conveyed by colour alone.
Follow the existing `data.Error` / `data.ErrorField` convention in this handler.

## Acceptance

- Handler test: adding an anchor for a date that already has one leaves exactly
  one anchor for that date, and the amount balances use is the intended one.
- A test that pins determinism: the same sequence of adds produces the same
  authoritative anchor every run.
- If rejection: an accessibility assertion on the error, per `ACCESSIBILITY.md`.
- The doc comment on `latestAnchorAtOrBefore` matches the code.
- `go build ./... && go vet ./... && go test -race ./...` clean.

This task carries an `a11y` check in addition to the dual-family verification.
