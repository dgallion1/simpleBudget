# Z2 attempt 2 — manifest

## Files changed

- `internal/services/retirement/settings.go` — added
  `SaveWithRevisionIfScenario(settings *models.WhatIfSettings, expectedScenario string) (int, error)`,
  right after `SaveWithRevision`. Mirrors `ApplyOverrides`' locking pattern:
  the `expectedScenario == active-scenario` comparison and the write happen
  inside the SAME `sm.mu.Lock()`. Reuses `saveInternalAndBump` (the same
  locked write helper `SaveWithRevision` itself uses) rather than duplicating
  the write path. Mismatch returns `*ScenarioConflictError` and writes
  nothing.
- `internal/services/retirement/settings_test.go` — two new unit tests (see
  below), following `TestApplyOverrides_*`'s fixture style.
- `internal/handlers/whatif/handlers.go` — added `saveAndRecalcIfScenario`,
  a `saveAndRecalc` sibling that saves through
  `SaveWithRevisionIfScenario` instead of `SaveWithRevision`, reusing the
  shared `recalcAndRender` tail. `saveAndRecalc` itself and all its other
  callers (`handlers_rates.go` x7) are untouched.
- `internal/handlers/whatif/sync.go` — `handleWhatIfSyncApply` now saves via
  `saveAndRecalcIfScenario(w, r, settings, expectedScenario)` instead of
  `saveAndRecalc(w, r, settings)`. The early `ActiveFilename()` check remains
  as a fast-fail for UX; the doc comment now states plainly that it is not
  what makes the write safe, and explains why the plan_hash comparison does
  not need to be inside the lock (the plan saved is always the one
  recomputed fresh at apply time — only scenario identity can rot in the
  unlocked window). Added a test-only seam, `syncApplyRaceTestHook`
  (nil in production, invoked once, right before the save), so a test can
  deterministically land a scenario switch inside the exact window between
  the handler's own unlocked checks and the locked save — the window the
  proven defect exploited.
- `internal/handlers/whatif/sync_test.go` — one new handler-level test (see
  below).

## Tests added

1. `TestSaveWithRevisionIfScenario_RefusesWhenExpectedScenarioIsNotActive`
   (internal/services/retirement/settings_test.go) — active scenario is
   `whatif.json` (A); calls `SaveWithRevisionIfScenario` with
   `expectedScenario = "whatif_not-the-active-one.json"` (B) → asserts
   `*ScenarioConflictError`, revision 0, and — via `InvalidateCache` +
   reload — that the on-disk `MonthlyLivingExpenses` is byte-identical to
   before the call (file NOT written).
2. `TestSaveWithRevisionIfScenario_SavesWhenScenarioMatches`
   (internal/services/retirement/settings_test.go) — matching scenario →
   asserts a nonzero revision and that the value persists across
   `InvalidateCache` + reload.
3. `TestHandleWhatIfSyncApply_ScenarioSwitchDuringApplyWindowRejected`
   (internal/handlers/whatif/sync_test.go) — reproduces the proven exploit:
   preview while `whatif.json` is active, create+switch to a second scenario
   (`whatif_other-scenario.json` via `CreateScenario`), switch back to
   `whatif.json` so the handler's own fast-fail check passes, then use
   `syncApplyRaceTestHook` to switch to the OTHER scenario in the window
   between that check and the save (modeling a concurrent second
   tab/MCP call). Asserts: apply returns 409, AND — critically — reloads the
   OTHER scenario's file via `LoadScenarioSettings` and asserts its
   `MonthlyLivingExpenses`/income sources are byte-unchanged (the exploit's
   actual signature was a silent 200 that overwrote the OTHER scenario's
   file), AND that the originally-previewed `whatif.json` is also unchanged.

   Verified this test is load-bearing: temporarily reverted the handler's
   save call to `saveAndRecalc` (attempt-1 shape) and re-ran — the test
   failed with `status = 200, want 409` (vulnerable behavior reproduced,
   confirming the test actually exercises the fixed code path and not a
   tautology). Reverted back to the fix before the final run below.

4. Pre-existing attempt-1 tests unchanged and still pass:
   `TestHandleWhatIfSyncApply_SavesSyncedSettings`,
