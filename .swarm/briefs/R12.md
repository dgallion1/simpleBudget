# R12 — Project's byDay map drops every recurring occurrence (Tier 2)

## The defect

`internal/services/accounts/projection.go:116` declares:

```go
byDay := make(map[time.Time]float64)
```

Keys are WRITTEN at :136 as `occ`, derived from `dayOf(rp.NextExpected)` — the
recurring payment's date, which comes from parsed CSV transactions and is
therefore UTC. Keys are READ at :150 as `day`, derived from
`dayOf(asOf).AddDate(0, 0, d)` — where `asOf` is `time.Now()` on the default
MCP path, and therefore carries `time.Local`.

`dayOf` (balance.go:201-203) rebuilds the value **in its own argument's
Location**. Go compares `time.Time` map keys by struct fields, INCLUDING the
`*Location` pointer. The lookup therefore never matches.

**This fires on every host, not only non-UTC ones.** Reproduced standalone:

```
TZ=UTC
write key: 2026-09-01 00:00:00 +0000 UTC  loc=0x59c980 (UTC)
read  key: 2026-09-01 00:00:00 +0000 UTC  loc=0x5a1600 (UTC)
same instant? true   Equal()? true
map lookup found=false value=0
```

`time.Local` and `time.UTC` are distinct Location objects even when they denote
the same zone, so the keys differ despite `Equal()` returning true and the
instants being identical.

## Consequence

Every `time.Now()`-derived projection applies **zero** recurring outflows.
`Crossing` is never set, `Minimum` stays at the starting balance, and
`SuggestedTopUp` is 0 — regardless of the data. MCP `get_balance_projection`
called without an explicit `as_of` has been silently answering "healthy, no
top-up needed" for every account, on every platform.

The dashboard escapes it because `handlers.go:110` derives `asOf` from the
ledger's own `MaxDate`, which carries the transactions' Location.

This predates every task in run R. It was found by R5's adversarial checker
while building an unrelated counterfactual, and independently confirmed by
R5's primary checker and by the R5 judge panel.

## Scope

Fix the KEY, not `dayOf`.

**Do NOT change `dayOf`.** It is used by `BalanceAt`, `Freshness`, `Drift` and
`latestAnchorAtOrBefore`, all of which compare instants with `After`/`Before`.
Rebuilding it in UTC would move the day boundary for non-UTC inputs and change
balances — a much larger blast radius than this defect.

Change only how `byDay` is keyed inside `Project`, so that a write derived from
a UTC transaction date and a read derived from a Local `asOf` match when they
name the same calendar day. A `struct{ y int; m time.Month; d int }` key, or a
`"2006-01-02"` string key, both do this; pick one and say why.

Preserve the existing day-granularity semantics: the codebase's convention is
"the calendar day in the value's own location" (see `dayOf`'s doc comment).

## Attempt 2 (2026-08-19) — the key fix is right; the boundary it exposed is not

Attempt 1 FAILED the adversarial lane. The primary lane passed it, and the lead
resolved the factual disagreement by direct experiment rather than by convening
judges. Both lanes were partly right.

Your `calendarDay` key fix is CORRECT and stays. Do not revert it. The problem
is what it exposed.

### The defect

`Project` reasons about days two incompatible ways:

- The advance loop filters by INSTANT: `for ...; !occ.After(asOfDay); ...` —
  Location-agnostic, and the doc comment at :110-114 states the intent as
  "occurrences that fall strictly after asOf".
- The balance walk reads by LABEL, starting at `asOfDay.AddDate(0,0,1)` — it
  deliberately never visits asOf's own calendar day.

When `occ` and `asOf` carry the same Location those agree and nothing is lost.
When they differ — which is the normal case, `occ` from a UTC transaction date
and `asOf` from `time.Now()` — an occurrence can be strictly after `asOf` yet
carry a label the walk never reads. It vanishes silently.

Reproduced by the lead, Asia/Tokyo, asOf 2026-09-01 08:00 JST (= 2026-08-31
23:00 UTC), occurrence 2026-09-01 00:00 UTC, one real hour later:

    freq=yearly   -> crossing=(none)     minimum=800.00 topup=0.00   <-- $400 lost
    freq=monthly  -> crossing=2026-10-01 minimum=400.00 topup=100.00 <-- a cycle late

The monthly case is the dangerous one: it does not look broken. It reports a
plausible crossing date that is one whole cycle after the true one.

User consequence: an outflow due within the hour is not counted, and the tool
answers "healthy, no top-up needed".

### Required fix

Make the advance filter and the balance walk agree about what "day" means.
Normalise both sides into ONE frame before the advance loop — e.g. convert
`occ` into `asOf`'s Location (or both to UTC) and derive the label from the
normalised value — so an occurrence strictly after `asOf` is always written to
a label the walk visits.

Do NOT "fix" this by making the walk start at `asOfDay` instead of
`asOfDay+1`. The exclusion of asOf's own day is deliberate: an anchor states an
END-of-day balance, so a same-day movement is already reflected. Changing that
would double-count.

State plainly in your report which frame you normalised into and why, and what
happens to an occurrence that lands exactly on `asOf`'s instant.

### Evidence required, persisted in the tree

- A test for the yearly case above: the occurrence one hour after `asOf` under
  a positive-UTC-offset zone MUST be applied. It must FAIL against attempt 1.
- A test for the monthly case: the crossing must be the near date, not one
  cycle later.
- Both run under TZ=UTC, TZ=America/New_York and TZ=Asia/Tokyo, with `-count=1`
  and `time.Local` echoed from inside the test. Note attempt 1's pinning test
  deliberately chose dates "17 days apart... so the outcome is identical under
  any TZ" — a fixture that cannot exercise the boundary. Do not repeat that.
- A negative-offset zone case too (e.g. Pacific/Midway), where the skew runs the
  other way.
- Mutation check per fix, on a scratch copy outside the repo.
