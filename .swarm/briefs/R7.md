# R7 — resolve_transfer validates against empty or stale state (Tier 2)

## The defect

`internal/services/mcpsvc/ledger/resolve.go:85` validates the pair key with:

```go
suspected := deps.Transfers.SuspectedTransfers()
if !suspectedContains(suspected, key) { ...reject... }
```

`SuspectedTransfers()` (`internal/services/dataloader/transfers.go:76`) returns
the review queue **from the most recent load**. It is populated only by
`setTransferState`, which runs during `LoadDataContext`. `resolve_transfer`
never triggers a load.

So:

- On a fresh server, before any endpoint has happened to load data, the queue is
  empty and **every valid pair key is rejected**.
- After the underlying CSVs change, the cached queue is stale and a pair that is
  no longer suspected can still be resolved.

The existing tests hide both by explicitly preloading the queue.

## Scope

- Refresh the ledger before validating the pair key, using the existing
  `deps.load()` helper on `Deps` (`internal/services/mcpsvc/ledger/register.go`)
  — it already routes through `TransactionSource.LoadData`, which is what
  repopulates the suspected queue, and it reports a locked store properly rather
  than letting ciphertext surface as a parse error.
- Re-validate before writing, not only before minting the confirm token. The
  approval round trip means time passes between the two.
- Update the existing resolve tests to **stop preloading the queue**. If a test
  only passes because it preloaded, it was not testing the tool.

## Hard constraint — do not widen this task

Implement inside `internal/services/mcpsvc/ledger/resolve.go`.
