# R5 — get_balance_projection must honour as_of (Tier 2)

**Depends on R3, which lands first in the same function. Rebase onto it.**

## The defect

`internal/services/mcpsvc/ledger/accounts.go` parses an explicit `as_of` for
`get_balance_projection` (around line 211) and passes it to `accounts.Project`
— but the recurring-payment input is built by `recurringForProjection`, which
calls `insights.DetectRecurring(ts)`.

`DetectRecurring` is defined as `DetectRecurringAt(ts, time.Time{})`
(`internal/services/insights/recurring.go:196`), and a zero reference date
falls back to the set's own `MaxDate`. Read the `DetectRecurringAt` doc comment
— it states that `referenceDate` does two distinct jobs: it truncates the
history detection sees, **and** it is the freshness "now" each candidate series
is checked against.

Consequences:

- A **historical** `as_of` runs detection over the whole ledger including
  transactions after that date, so the forecast uses future evidence — and can
  schedule nothing inside its own window.
- A **future** `as_of` evaluates recurrence freshness against the ledger
  maximum rather than the requested date.

## Scope

In `get_balance_projection` only:

- Truncate the active transaction set at `as_of` before projecting.
- Call `insights.DetectRecurringAt(ts, asOf)` instead of `DetectRecurring(ts)`.

`recurringForProjection` needs the as-of date threaded in. `get_accounts` uses
`time.Now()` and is not in scope beyond R3's active-set change.

## Acceptance

- A historical `as_of` schedules recurrence from evidence at or before that date
  only, and **can** schedule inside its window (assert a non-empty schedule on a
  fixture where the old code produced none).
- A future `as_of` evaluates freshness against the requested date, not the
  ledger maximum.
- With no `as_of` supplied, output is unchanged from current behaviour on a
  fixture — pin this so the default path cannot drift.
- `go build ./... && go vet ./... && go test -race ./...` clean.


## Attempt 2 (2026-08-19) — both lanes FAILED attempt 1

The historical and future as_of behaviour is CORRECT and both lanes confirmed it.
Do not redo that. Attempt 1 failed because it silently changed the DEFAULT
(no as_of) path in three ways:

1. **Recurring reference date.** Pre-R5 the default called
   `insights.DetectRecurring(ts)`, whose zero reference date falls back to
   `ts.MaxDate()`. Attempt 1 routes the default through
   `DetectRecurringAt(ts, time.Now())`. Those differ whenever the ledger's last
   row is not dated today — the normal case for imported CSVs. Proven: a
   future-dated paired transfer fixture returns has_reference=true /
   reference_amount=777.00 pre-R5 and false / 0.00 now.

2. **Reference amount.** `medianInboundPairedTransfer` (projection.go:249-265)
   applies no date filter of its own, so the new truncation silently became its
   only filter. Default path, inbound transfers 100/200 past plus 900 at
   today+10: reference_amount 150.00 now vs 200.00 before.

3. **Off-by-one day, timezone dependent.** `tx.Date` is UTC; `time.Now()` is
   Local; `FilterByDateRange` (transaction.go:224-225) builds the boundary in
   `end.Location()`. Same fixture yields reference_amount 200.00 under EDT and
   150.00 under TZ=Asia/Tokyo. `BalanceAt` excludes a row the truncation
   includes — two boundaries inside one call disagreeing. Explicit as_of is
   unaffected because it parses to UTC, which is exactly why the committed tests
   miss it.

### Required fix — the simplest thing that guarantees criterion 3

Branch on whether as_of was SUPPLIED:
- **as_of absent:** take the pre-R5 path verbatim — no truncation, and
  `insights.DetectRecurring(ts)` with its MaxDate fallback. Criterion 3 then
  holds by construction rather than by fixture choice.
- **as_of present:** the new truncated + `DetectRecurringAt(ts, asOf)` path,
  which both lanes already confirmed correct.

Additionally, normalise as_of to a day boundary with the existing `dayOf`
convention (balance.go:201-203) before calling FilterByDateRange, so the
truncation boundary and BalanceAt's boundary agree.

### Evidence required, all persisted in the tree
- A default-path test on a fixture that ACTUALLY EXERCISES the difference: one
  containing a future-dated inbound paired transfer, asserting reference_amount.
  Attempt 1's pin was vacuous in both dimensions — its fixture had no transfers
  and no merchant with 3+ occurrences.
- A test pinning the today/tomorrow edge that FAILS under a non-UTC TZ if the
  boundary is wrong. Run it under at least two TZ values.
- Mutation check per fix, on a scratch copy outside the repo.
