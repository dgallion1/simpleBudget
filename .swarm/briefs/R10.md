# R10 — consent-path coverage gaps (Tier 1, test-only)

Both R4 verification lanes independently found these while accepting R4. They
are coverage gaps, not code defects: R4's binding is correct and confirmed.

## Gap 1 — the two money-writing tools have no browser round-trip test

`internal/services/mcpsvc/admin/` has six end-to-end browser-approval tests
(`TestRestoreRunsWhenApprovedInTheBrowser` and friends) driving a real
in-memory MCP client/server through the full approval round trip.

`internal/services/mcpsvc/ledger/` has none. Grep confirms no `Approvals` or
`BaseURL` anywhere in `ledger/*_test.go`. So for `set_balance_anchor` and
`resolve_transfer` the browser rung of the consent ladder rests on the shared
registry oracle plus structural inspection of the call sites — not on an actual
round trip.

That is backwards. The two tools with no round-trip coverage are the two that
write money data; the two that have it are the admin tools.

## Gap 2 — nothing pins the consequence prose

`anchorConsequences` (ledger/anchor.go) and `resolveConsequences`
(ledger/resolve.go) produce the text a human reads before approving. R4 binds
the approval to the exact operation — but if this prose later drifts to
describe a different amount, date or verdict, the binding would faithfully
authorize an operation the human misread. No test asserts the text.

R4's checker verified it unchanged since 1a8636d only by diff.

## Scope — TEST ONLY

Add tests to `internal/services/mcpsvc/ledger/`. Change no production code. If
you conclude production code must change, STOP and report instead.

Do NOT add files under `internal/services/mcpsvc/confirm/` — it is a
`.swarm/critical.globs` entry and touching it escalates this task's tier for no
benefit. Both consequence functions live in `ledger/`, so nothing requires it.

Model the round-trip tests on the admin package's existing ones
(`internal/services/mcpsvc/admin/approval_test.go`); reuse that shape rather
than inventing a new harness.

## Acceptance criteria

1. An end-to-end browser-approval round trip for `set_balance_anchor`: the tool
   returns an approval URL, a human decision is recorded out of band, the
   re-invoked call consumes THAT decision, and the anchor is written. Assert the
   written amount is the one the approval described.
2. The same for `resolve_transfer`, including a refusal path: a human answering
   NO must leave `transfer_decisions.json` byte-unchanged.
3. A test pinning the load-bearing facts in `anchorConsequences` — that the
   rendered text contains the account id, the amount and the date it is about to
   write. Assert on the FACTS, not on incidental wording; a test that breaks on
   a typo fix is a liability.
4. The same for `resolveConsequences`: pair key and verdict.
5. Prove the prose tests discriminate: on a scratch copy OUTSIDE the repo, change
   the consequence text to describe a different amount / the opposite verdict,
   confirm your tests fail, restore. Report it.
6. Stability: these involve an in-memory client/server and a blocking await. Run
   your new tests at least 20 times under `-race` and report the pass count. It
   must be 20/20. This repo has had one flaky test already; do not add another.
7. `go build ./... && go vet ./... && go test -race ./...` clean.

Write `.swarm/manifests/R10.1.files`. Report the discrimination result, the
20-run count, and each criterion with its evidence.
