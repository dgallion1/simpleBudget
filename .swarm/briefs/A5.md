### Scope

Add a funding projection to `internal/services/accounts`: given an account and
the transaction set, roll its balance forward and report whether it will dip
below its low-balance threshold, and what to move if so.

You are NOT implementing UI (the dashboard card is A8) or MCP tools (A9).

### Behavior

1. **Roll forward 35 days** from a caller-supplied "as of" date, starting from
   `BalanceAt(acct, txs, asOf)`. Apply expected recurring items for **this
   account only** — filter the recurring engine's output to transactions whose
   `AccountID` matches. Advisory only: **never write anything**.
2. **No anchor → no projection.** If `BalanceAt` reports `Available: false`,
   return a result saying so. Do not project from an assumed zero; an unknown
   balance and a zero balance are different facts and the UI renders them
   differently.
3. **Threshold.** Use the account's `LowBalanceThreshold`; when it is zero,
   use a package-level default of **500**. Report the first date the projected
   balance crosses below it, and the minimum projected balance over the window.
4. **Suggested top-up** = the shortfall (threshold minus the minimum projected
   balance) **rounded up to the nearest $100**.
5. **Reference amount** = the median of confirmed inbound paired-transfer
   amounts into this account, so the UI can say "you usually move $X". A
   transfer leg is inbound to this account when it is `TransactionType ==
   models.Transfer`, `TransferClass == "paired"`, its `AccountID` is this
   account, and its amount is positive. With no such history, report that
   there is none rather than inventing a number.
6. **No crossing** → report that plainly; callers must be able to distinguish
   "healthy" from "unknown".

Design the exported types and function signature yourself; keep them in
`internal/services/accounts` alongside A4's, and name them so a reader can tell
projection results from balance results.

### Money handling

Amounts are `float64`. Do not compare with `==`; use the epsilon convention
already in `internal/services/accounts` tests. Round only for presentation and
for the deliberate $100 rounding in (4) — never in intermediate arithmetic.

### Tests

Cover at minimum: a crossing with the correct first-crossing date and minimum;
no crossing; no anchor (unavailable, not zero); the default-vs-override
threshold; the $100 rounding at an exact boundary and just past one; the median
reference with an even and an odd number of prior transfers; no prior transfers;
and that recurring items belonging to OTHER accounts do not affect this
account's projection.

Stub or construct the recurring input rather than depending on real detection
heuristics, so the test asserts your projection maths and not the engine's.
Precede any loop assertion with a count assertion (ruling 2026-08-16e).
