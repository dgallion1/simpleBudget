### Why this task exists

Every user decision the app stores — pins, near-duplicate resolutions, Amazon
enrichment — is keyed on `Transaction.Hash`, which is
`sha256(date|lowercased description|amount)[:8]`. Because the description is
part of that identity, a bank reformatting its description text silently
orphans every decision the user ever made about those rows. StableID removes
the description from the identity.

In `internal/models`:

```go
func StableIDFor(accountID string, date time.Time, amountCents int64, occurrence int) string
```

returning exactly `accountID|YYYY-MM-DD|amountCents|occurrence`, e.g.
`usaa-checking|2025-05-04|-1234|0`. It must be deterministic and must vary with
the occurrence index.

On `DataLoader`:

```go
func (dl *DataLoader) PinFor(tx models.Transaction) (string, bool)
func (dl *DataLoader) WriteTransactionPins(pins map[string]string) error
```

`PinFor` resolves a transaction's pinned major-expense ID, **trying its
StableID first and falling back to the legacy `Hash`**. `WriteTransactionPins`
persists a pin map verbatim — it exists so tests can stage a legacy-keyed
sidecar; do not make it rewrite keys.

### Behavior

1. **Assignment.** During load, every transaction gets a `StableID` of
   `accountID|YYYY-MM-DD|cents|n`:
   - `accountID` is the row's `AccountID`; for unassigned rows use
     `file:<basename>` (e.g. `file:mystery.csv`).
   - the amount is **post-sign-normalization**, in integer cents, so a
     credit-kind flip is reflected in the identity.
   - `n` is the 0-based occurrence index among rows identical in those first
     three components, counted **in file order**.
2. **Sidecar resolution.** Lookups in the pins, duplicate-decisions and
   Amazon-enrichment stores try the StableID first and fall back to the legacy
   `Hash`. An existing sidecar written under legacy hashes must keep working
   with no migration step and no user action.
3. **Rewrite on save.** When a store is next written, resolved entries are
   rekeyed to StableID, so the legacy dependency decays over time. A legacy key
   that no longer resolves to any loaded transaction is left alone rather than
   dropped — the row may simply be outside the current date range.
4. **`Hash` stays.** Do not remove or change `ComputeHash`. It remains the
   fallback key and is still used by dedup. **Dedup behavior must not change at
   all** — StableID is an identity for user decisions, not a dedup key.

### The known limitation, to be honest about

The occurrence index depends on export row order being stable across
re-exports. That is true for append-style bank exports and is documented in
GLOSSARY.md. Do not try to engineer around it; do not invent a tiebreaker that
reintroduces the description.
