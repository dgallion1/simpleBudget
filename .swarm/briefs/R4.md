# R4 — Bind a browser approval to the exact operation shown (Tier 3)

## The defect

`internal/services/mcpsvc/confirm/approvals.go` keys pending approvals on
`(tool, subject)` alone:

- `Create` (line 70) deletes **every** existing pending with the same tool and
  subject before filing the new one.
- `Find` (line 118) returns the first pending matching tool and subject.

The subject is coarse. For `set_balance_anchor` it is only the account ID; for
`resolve_transfer` only the pair key. So two concurrent invocations that differ
in the facts a human actually reads — a different amount, a different date, the
opposite verdict — collide:

1. Invocation A files its approval and the user is shown A's amount.
2. Invocation B files one for the same account; `Create` deletes A's.
3. A's `awaitApproval` calls `Find(tool, subject)` and gets **B's** record.

A user approving "set the anchor to 500.00" can authorize a write of 5000.00,
and approving a transfer *reject* can authorize the *confirm*. This is the
consent boundary for every guarded mutating tool, which is why this task is
Tier 3.

## Required API (pinned — the acceptance oracle calls these exact signatures)

```go
func (a *Approvals) Create(tool, subject, opID, title, detail string) (*Pending, error)
func (a *Approvals) Find(tool, subject, opID string) (*Pending, bool)
```

`opID` is the operation identity. **Use the confirm token** — it is already
minted against the exact argument struct (`deps.Confirm.Mint(tool, args)`) and
is already in scope at all four call sites, in both the `askForApproval` and
`awaitApproval` branches. Verify that for yourself at each site before editing.

Replacement semantics change accordingly: `Create` replaces an existing pending
only when **all three** of tool, subject and opID match. Different operations on
one subject coexist.

`askForApproval` and `awaitApproval` take the operation id through to
`Create`/`Find`.

**Correction (2026-08-19, found by the R4 primary arm — the original brief was
wrong here).** There are TWO textually identical copies of these helpers, one
per package, each taking its own package's `Deps` type:
`internal/services/mcpsvc/ledger/approval.go:25,50` and
`internal/services/mcpsvc/admin/approval.go:27,52`. Both must receive the
identical opID-threading edit or the admin package will not compile. This is
required work, not scope creep.

Update all four guarded call sites:

- `internal/services/mcpsvc/ledger/anchor.go` (`set_balance_anchor`)
- `internal/services/mcpsvc/ledger/resolve.go` (`resolve_transfer`)
- `internal/services/mcpsvc/admin/restore.go` (`restore_backup`)
- `internal/services/mcpsvc/admin/shutdown.go` (`shutdown_server`)

## What must not change

- The consent ladder and its ordering (browser → in-client form → token alone),
  documented at the top of `approval.go`.
- The detail text shown to the human continues to name the load-bearing facts
  concretely (see `anchorConsequences`).
- `RequestState` stays an untrusted breadcrumb — the pending record is still
  re-found server-side, never trusted from the client.
- A decided request stays decided; a second `Decide` still reports
  `ErrNoSuchApproval`.
