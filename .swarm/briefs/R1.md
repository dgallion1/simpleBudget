# R1 — Serialized read-modify-write for the accounts sidecar (Tier 3)

## The defect

`internal/handlers/accounts/handlers.go` and
`internal/services/mcpsvc/ledger/anchor.go` each do a bare
load → modify → save against `accounts.json`, with nothing serializing them:

- `applyForm` (handlers.go:400-466) — `accounts.Load(store)`, edit, `accounts.Save(store, accts)`
- the add-anchor handler (handlers.go:244-275) — same shape
- the delete-anchor handler — same shape
- `applyAnchor` (anchor.go:186-215) — `deps.Accounts.LoadAccounts()`, edit, save

Two consequences, both verified against the current tree:

1. **Lost writes.** Two concurrent requests each load the same set, each apply
   their own edit, and the second save discards the first edit entirely.
2. **Resurrected state.** A restore that lands between a request's load and its
   save is undone by that save, which persists accounts derived from
   pre-restore contents — while the restore reports success.

There is **no mutex anywhere in `internal/services/accounts/`**. Confirm this
yourself before starting.

## The precedent you must follow (do not invent a new approach)

`internal/services/storage/storage.go:627` already provides `BeginShared()`
returning a `*SharedTx`, and its doc comment describes *exactly* this failure —
read it in full before writing any code. `internal/services/dataloader` already
pairs it with its own `writeMu`. The accounts sidecar simply never adopted the
pattern. Adopt it.

## Required API (pinned — the acceptance oracle calls this exact signature)

In `internal/services/accounts`:

```go
// Mutate serializes a load-modify-save of the accounts sidecar. fn receives
// the currently stored accounts and returns the set to save. The load, fn and
// the save happen inside one held section, so concurrent mutations do not lose
// each other's writes and a restore cannot land between the load and the save.
// An error from fn aborts the mutation without saving.
func Mutate(s *storage.Storage, fn func([]models.Account) ([]models.Account, error)) error
```

Every one of the four call sites above must go through it. No `accounts.Save`
or `SaveAccounts` call may remain in `internal/handlers/accounts/` or
`internal/services/mcpsvc/ledger/` outside a `Mutate` callback.

## Lock-order constraint — violating this deadlocks the app

From `storage.go`, and non-negotiable:

- The caller's own serialization (your package mutex) is taken **outside**
  `BeginShared`, never the reverse.
- Nothing holding the data lock in either mode may then wait on that
  serialization.
- Nothing inside a shared or exclusive section may call the plain `Storage`
  write methods — `sync.RWMutex` is not reentrant and a second `RLock` while a
  restore is queued for the write lock blocks forever. Use the section's own
  `ReadFile`/`WriteFile`.
- A transaction may span storage calls and pure computation on their contents,
  and must **not** span a call into another service.

## Acceptance

`.swarm/tier3/R1/accept.sh` is the oracle and it is authoritative. It checks:
build, vet, the pinned signature, that no unserialized save survives at the
call sites, three lead-authored tests under `-race`
(`.swarm/tier3/R1/oracle/zz_oracle_r1_test.go` — concurrent mutations lose no
writes; an fn error saves nothing; `BeginExclusive` is *not* granted while a
`Mutate` section is open), and the full suite under `-race`.

You may not edit the oracle test or `accept.sh`. Run
`bash .swarm/tier3/R1/accept.sh` yourself before reporting done, and paste its
output into your manifest.

Existing accounts tests must keep passing unchanged. Behaviour visible to users
does not change — this is a concurrency and durability fix only.
