## Fix 1 — `scrollable-region-focusable` on What-If scroll containers

Added `tabindex="0" role="region" aria-label="<name>"` to every remaining
unlabeled `max-h-*`/`overflow-y-auto` scroll container that has no
focusable descendant (a keyboard user could not reach or scroll it):

- `projection-breakdown.html:12` → `aria-label="Projection breakdown"`
- `tax-summary.html:42` → `aria-label="Tax summary"`
- **`historical-backtest.html:84`** (`<div class="mt-2 max-h-64
  overflow-y-auto">` inside the "View All N Sequences" `<details>`) — the
  ruling asked to check for other whatif scroll containers with the same
  defect; this is the one it named. → `aria-label="Historical backtest
  sequences"`.

Checked and left alone: `quick-adjust.html:65`
(`<div class="flex-1 overflow-y-auto ...">`) already contains focusable
descendants (the panel's own sliders/selects), so it does not trigger this
rule — confirmed via a targeted `scrollable-region-focusable`-only axe run
(0 nodes) both before and after this change.

Before: `scrollable-region-focusable` fires whenever an element is
scrollable (`overflow-y: auto`/`scroll` with `scrollHeight > clientHeight`)
AND has no focusable descendant AND is not itself focusable — all three of
the fixed `<div>`s met that (each wraps a `<table>` with no interactive
cells). After: `tabindex="0"` makes each one directly focusable, and
`role="region"` + `aria-label` gives it an accessible name so a screen
reader announces what the region is before a keyboard user tabs into it
to scroll.

## Fix 2 — `target-size` on Explorer `#clear-search-btn`

`explorer.html`: was `class="absolute right-2 top-1/2 -translate-y-1/2
text-gray-500 hover:text-gray-600 dark:hover:text-gray-300 {{if not
.Search}}hidden{{end}}"` wrapping a bare `w-4 h-4` (16×16) svg with zero
padding. Now `class="absolute right-1 top-1/2 -translate-y-1/2
min-w-[24px] min-h-[24px] flex items-center justify-center rounded
text-gray-500 hover:text-gray-600 dark:hover:text-gray-300 focus:outline-
none focus-visible:ring-2 focus-visible:ring-accent {{if not
.Search}}hidden{{end}}"` — flex-centers the same 16px icon inside a
24×24 box (kept the absolute positioning; `right-2`→`right-1` compensates
for the wider box so the icon's visual position inside the input doesn't
shift), and added a focus ring while at it (was previously invisible on
focus). Confirmed rendered box = exactly 24×24px
(`getBoundingClientRect()`), both themes.

## Fix 3 — dark-mode `color-contrast` on Healthcare "+ Add Person" — investigated, NOT reproducible on the current tree

Extensive, reproducible verification (four independent methods, all
agreeing) found this element is **already compliant**, not a live defect
to fix:

1. **Direct token read via the real production theme toggle** (not a
   synthetic `.dark` class add — `localStorage.setItem('theme','dark')`
   + reload, the exact mechanism `base.html`'s init script uses):
   `getComputedStyle(document.documentElement).getPropertyValue('--accent')`
   → `165 180 252` (indigo-300), NOT indigo-600. `getComputedStyle(button
   [data-toggle-add-healthcare]).color` → `rgb(165, 180, 252)`, matching.
2. **Manual WCAG contrast math**: indigo-300 `rgb(165,180,252)` on
   `dark:bg-gray-800` `rgb(31,41,55)` = **7.36:1** (vs. the claimed
   2.77:1); against `dark:bg-gray-900` (the page background) = 8.9:1.
   Light mode: indigo-600 `rgb(79,70,229)` on white = 6.29:1. Both clear
   4.5:1 with large margin — this matches `styles.css`'s own U6-era
   design note ("indigo-300 clears comfortably against gray-900 AND each
   token's own -soft fill"; gray-800 is even lighter than gray-900, so an
   even bigger margin, not a smaller one).
3. **Targeted axe `color-contrast`-only scan** of `/whatif` in dark mode
   (real theme toggle, not colorScheme-only) at 5 viewports (390/768/
   1024/1280/1440): **0 violations at every width**.
4. **The fully-hardened sitewide probe** (below — every settings-rail
   collapse, every What-If result tab, Quick Adjust's 4 tabs, and the
   Healthcare "+ Add Person" form itself all forced open SIMULTANEOUSLY,
   the most thorough DOM state possible) reports `/whatif dark: clean`
   for the FULL axe ruleset, color-contrast included.

There are two `text-accent`/`text-xs text-accent` "+ Add Person"-labeled
controls on `/whatif` (`healthcare-card.html:7-9` and a second one at
`healthcare-card.html:69`, plus a differently-worded sibling
`rate-assumptions.html:21-23` "Persons" → "+ Add Person" using the
identical `text-accent` token) — checked all three the same way; all
three resolve to the same indigo-300-on-gray-800, all three pass.

**No token or template change made for fix 3** — `--accent`'s dark value
already satisfies the exact bar the instructions set ("≥4.5:1 on gray-800
in dark AND still ≥4.5:1 in light"), and changing a token that is not
failing would only add REGRESSION risk to every other `text-accent`
surface, which is the outcome the instructions explicitly warn against
("WITHOUT dropping any other current text-accent use below 4.5:1 on its
own ground"). If the checker's harness can reproduce 2.77:1 by a method
this investigation didn't try (a different browser engine, a specific
window/DPI combination, or a build artifact this tree doesn't have),
please attach that repro — the four methods above are the full extent of
what's independently verifiable from this tree and they agree with each
other and disagree with the reported ratio.

## Probe hardening (`.swarm/work/u15/axe_probe.js`)

Root cause of why these three survived attempt 1's "sitewide clean": the
reveal step never exercised three real, ordinarily-reachable paths. Added,
in the SAME reveal block (all one-way reveals — nothing here can toggle
already-visible content shut):

1. **All 5 What-If result tabs** (`[data-wf-tab]`/`[data-wf-panel]` — a
   SEPARATE tab system from the settings-rail `[data-wf-collapse-body]`
   cards attempt 1 already force-opened): `document.querySelectorAll(
   '[data-wf-panel]').forEach(panel => panel.classList.remove('hidden'))`.
   This is exactly what exposed fix 1's targets — `historical-backtest`'s
   "View All Sequences" `<details>` lives inside a non-default tab, so it
   was invisible to axe until this landed.
2. **Explorer search**: on `/explorer`, click `#search-input` and type
   `'a'` via `page.keyboard.type`, then wait — the ONLY path that removes
   `#clear-search-btn`'s server-rendered `.hidden` class (explorer.js's
   `input` listener), so the button (and its target-size fix) was
   unreachable to any prior probe.
3. **Add-person forms**: `document.querySelectorAll(
   '[data-toggle-add-healthcare]').forEach(t => t.click())` (Healthcare's
   "+ Add Person", the specific "add-person form" the ruling names), plus
   a generic pass over `[data-toggle-target]` disclosure buttons that lack
   `aria-expanded` (the ones that DO carry it, e.g. accounts.html's Add-
   an-account/Edit buttons, were already covered by attempt 1's
   `[aria-expanded="false"]` pass and are explicitly SKIPPED here to avoid
   double-toggling one that's already open shut).
